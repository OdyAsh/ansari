DIFFERENCES FROM PYTHON (deliberate)
- The routes are /whatsapp/v3 (owner decision; Meta's callback URL must be changed at cutover, a phase 7 step).
- Raw bytes are read first and parsed by hand AFTER the signature check, so an unsigned caller learns nothing about the body. FastAPI checked the signature in a dependency before parsing; `express.json()` would parse first.
- Invalid UTF-8 is refused with a 400 (INVALID_PAYLOAD), as Python's json.loads does.
- The JSON parser's own error text is never returned or logged (it quotes the start of the body, i.e. the user's message). Python returned `str(e)`. The answer says only "Webhook body is not valid JSON".
- Any non-parser error in the read step is answered with a fixed text; Python returned `str(e)`.
- Body limit 1 MB (413). Python had none.
- Express has no 405: a wrong method on a known path is a 404.
- A preflight from a disallowed origin gets no CORS headers (Python's Starlette answered 400). Meta's servers send no Origin header.
- The caller's own X-Request-ID is ignored (it is untrusted text going into the logs).
- Sentry: Python sampled traces and profiles (20% in production) and filtered log events containing "HTTP exception: 401/403". Neither is ported: a trace records the request URL (the handshake URL holds the verify token), and nothing here sends log lines to Sentry. Events are scrubbed as in apps/auth (method, URL without query string, three harmless headers) and carry no breadcrumbs.
- Graceful shutdown on SIGTERM/SIGINT (stop accepting, wait up to 8 s for background work, flush Sentry) is new: uvicorn did this implicitly in Python.
- Background work runs in `BackgroundTasks`, the one place that catches, logs and reports (`background_processing_failure`); a failure there never becomes an unhandled rejection (tested).
- Python's `get_*` singletons and `reset_*` functions are gone; `createServices` chooses real or mock once at start-up.

KNOWN LIMITS
- tests/app.test.ts is 96 tests in one file against the real app on a real port; it takes about 1 s but depends on the machine allowing 127.0.0.1 listeners.
- 8 s of grace on shutdown is a guess at Railway's limit (documented as about that), not measured.
- `index.ts` itself (the wiring, signal handlers and the unhandledRejection hook) is not unit tested: only run by hand against the built file. Its pieces (createServices, gracefulShutdown, BackgroundTasks, sentryReporter) are.
- The `unhandledRejection` hook logs and reports but does not exit; I chose that so one bug cannot take the whole service down, but it also hides a corrupt state. Open for the owner's view.
- The lockfile gained 15 lines for this app only (0 removed).

DIFFERENCES FROM PYTHON (deliberate)
- One `ConversationManager` serves every message; per-message state (token, typing indicator) is a `Turn` object. Python built a manager per webhook.
- `triage()` returns what should happen and the HTTP layer (phase 5) maps it to status codes, then calls `dispatch()`. Python mixed both in the route.
- Settings, clients and the clock are passed in, not read from globals.
- A whitespace-only answer splits into nothing (phase 2 fix); the user gets "Sorry, we couldn't process your message. Please try again later." as for an empty answer. This is the phase-2 requirement, now implemented and tested.
- Two Python branches are not ported because they cannot be reached here: a thread-creation reply without an id (the apps/api client already refuses it) and an answer that formats to empty text (the formatter never empties non-empty text).
- Python's `isoformat` read of `last_message_time` refused a timestamp with no time zone; JavaScript would read it as server-local time. A regular expression requires `Z` or an offset and anything else is treated as an unexpected fault (user gets the "unexpected error" notice).
- Python's `str.split()` and JavaScript's `\s` differ (BOM, U+001C-U+001F, U+0085); a hand-written `pythonSplitWords` is used for the thread title and checked against Python's full list.
- The typing indicator is an `AbortController`-driven loop instead of an asyncio task. Python's "cancel" ends the sleep at once; so does `abort()` here.
- Python caught `Exception` in `handle_text_message`; here an unexpected fault is caught by the same outer handler, logged with its error, and gets the "unexpected" notice. The typing indicator is now stopped in a `finally`, so every exit ends it (Python cancelled it only on some exits).

KNOWN LIMITS
- `dispatch()` is awaited by its caller. The un-awaited call with a catch-all (so a failure is never lost) is phase 5's job, as the plan says. Nothing here throws in normal use, but I did not prove that for every possible fault, only for the ones in the tests (including a RangeError from apps/api).
- Mock-only: the in-memory clients do not behave like the real services when a token changes (the mock gives each token its own threads), so the retry tests replace the thread calls to isolate the retry rule.
- The "Sentry" reporter is a function passed in; the real Sentry sender is wired in phase 5.
